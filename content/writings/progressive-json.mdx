Why most APIs send JSON still make us wait — and how Progressive JSON can change that.

Imagine you have a JSON object representing a blog post with header, content, comments, and footer:

```json
{
  "header": "Welcome to my blog",
  "post": {
    "content": "This is my article",
    "comments": ["First comment", "Second comment"]
  },
  "footer": "Hope you like it"
}
```

If you want to send this over the network in the classic way, the client has to wait for the entire JSON to arrive before parsing and using it. That means even if the comments take a long time to fetch on the server, nothing shows up on the client until everything’s ready.

And yet, this is how almost all apps send JSON today.

You might think: why not use a streaming JSON parser that can work on partial data? It can parse the first part:

```json
{
  "header": "Welcome to my blog",
  "post": {
    "content": "This is my article",
    "comments": ["First comment", "Second comment"]
  }
  // footer is still missing
}
```

Sounds better, but here’s the problem: this partial JSON is malformed or incomplete. The client can’t be sure if more comments or properties are coming or if this is the final data. This breaks assumptions in application code that expects fully formed objects.

This is like loading a JPEG image from top to bottom — you see only the top 10% clearly, but the rest is missing or blurry. The picture is incomplete, so it’s hard to make sense of.

## The real issue: depth-first streaming delays everything

This incomplete streaming happens because JSON is sent depth-first, one property after another, in document order. If one piece is slow (say, comments loading from a slow database), it blocks everything that comes after it.

Even browsers streaming HTML follow this order. You get a partial page, but if the footer is ready before comments, it still waits behind slow content.

The key problem: when you stream in order, a slow part blocks everything else.

## Enter Progressive JSON — breadth-first streaming with placeholders

What if instead of depth-first, we stream breadth-first?

Imagine sending this skeleton JSON first:

```json
{
  "header": "$1",
  "post": "$2",
  "footer": "$3"
}
```

Here, "$1", "$2", and "$3" are placeholders representing data chunks to come later. The client gets the whole structure immediately and can start rendering or working with it. As the actual values arrive, the client fills in the placeholders incrementally.

This way, slow parts don’t block fast parts — and the client always has a consistent, well-formed object to work with.

Why Progressive JSON matters:

- Allows incremental delivery of structured data
- Improves perceived performance and resource usage
- Avoids blocking on slow parts of the data tree
- Keeps client-side logic simple, as objects remain valid throughout streaming
