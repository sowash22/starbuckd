More tools don’t make AI agents smarter. They can make them dumber.

You probably have seen it — when you keep bolting the same agent onto tools like calendars, messages, databases, search APIs, analytics dashboards, thinking more capability equals better answers — then watch performance crater.

Here’s what’s actually happening.

## The Context Tax

Every tool you add eats tokens. Not just the function name — the full schema:

- Function name + description (50–100 tokens)
- Every parameter with type definitions (20–50 tokens each)
- Argument descriptions and constraints (30–80 tokens each)
- Return type specifications (20–40 tokens)

A single well-documented tool consumes 200–400 tokens. At 15 tools, you’ve burned 3,000–6,000 tokens before the agent even starts reasoning.

Then the cascade begins. Each tool call adds response data to the context window. The model has to track:

- Which tools it’s already called
- What each returned
- How those results inform the next step
- Whether to try a different tool or proceed

Multi-step tasks compound this fast. Three sequential tool calls across 15 available tools? You’re now managing tool selection state across \(15^3\) theoretical paths while your context window fills with API responses.

The model doesn’t just slow down. It loses coherence. It forgets what it learned from the second tool call by the time it’s evaluating the fifth.

## The 6–7 Rule

Through testing dozens of production deployments, the pattern is consistent. LangChain’s February 2025 benchmarks confirm it: agent performance degrades as both context and tool count increase.

Optimal range: 6–7 tools

- Fast tool selection
- High confidence in routing
- Minimal back-and-forth
- Clean, actionable outputs

Beyond 7 domains:
- GPT-4o performance dropped to 2% when increasing context to 7 domains.
- Even top models like Claude 3.5 Sonnet and o1 showed measurable degradation with added context.

## What to do instead

Consolidate ruthlessly. Tools can handle multiple operations under the hood.

- Instead of separate `list_users`, `list_events`, and `create_event`, build one `schedule_event` tool that finds availability and schedules in one call.
- Instead of `get_customer_by_id`, `list_transactions`, and `list_notes`, create `get_customer_context` that compiles everything at once.

Name tools like actions, not infrastructure. Use task-oriented names that describe what the tool does: `search_customer_records` beats `database_query_endpoint`. Namespacing helps too — `asana_search` and `jira_search` create clear boundaries when you have dozens of tools.

Return only high-signal context. Strip out technical noise like UUIDs, mime types, and low-level identifiers. Return `name` and `file_type` instead of `uuid` and `256px_image_url`. Natural language identifiers reduce hallucinations significantly.

Build more specialized agents instead of generalized agents.

The best agent does fewer things better. Not more things worse.
